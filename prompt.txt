1. Setup (admin-editable)
- 8 teams, 11 player categories, 8 players per category (88 players total)
- Every value below is editable in a Setup page: bid-ladder threshold, both bid steps, and all multipliers

2. Teams (name, colour)
- Shakuni Strategists #8E5CF5
- Krishna Crusaders #2D8CFF
- Yudhisthira Yodhas #F2B705
- Bhima Bashers #E5484D
- Pandava Warriors #FF7A1A
- Abhimanyu Avengers #12B886
- Arjuna Archers #20C4E8
- Karna Chargers #E34BA9
- Each team has a ₹18 Cr budget and must end with exactly 11 players, 1 from each category

3. Categories and base prices (Lakhs)
- All-rounder 1: 90, All-rounder 2: 80
- Batsman 1: 70, Batsman 2: 40, Batsman 3: 30
- Bowler 1: 60, Bowler 2: 50, Bowler 3: 30
- Impact player 1, 2, 3: 20 each

4. Owners
- Each team has exactly 2 owners, entered by the admin before the auction
- Owner fields: name, optional link to a player, optional captain tick
- An owner can be a player, a player and a captain, or neither

5. Owner-player (pre-auction)
- If an owner is also a player, auto-assign him to his own team at 3x his category's base price

6. Captains
- The admin pre-selects 8 captains (ordinary players from any categories, any mix)
- A captain's base price is his category's base price
- Captains are auctioned first, in random order, and no non-captain can come up until every team has a captain
- Each team gets exactly 1 captain
- The last remaining captain auto-goes to the last team without a captain at 3x base (example: ₹80 L becomes ₹2.4 Cr)
- A captain fills both the captain slot and his category slot

7. Remaining players
- After captains, each team buys 10 players, 1 from each category it doesn't hold yet
- The software generates the player order randomly, any category can appear at any time

8. Bid ladder
- +10 Lakhs while the current bid is below 200 (₹2 Cr), +20 Lakhs from 200 upward (190, 200, 220, 240)
- If a base price isn't a multiple of 10, the ladder continues from it (85, 95 ... 195, 205, 225)

9. Validation rules
- Minimum wallet: after every purchase a team must still hold at least 2x the base price of every category it hasn't filled. Reject any bid that would break this.
- Category penalty: the 8th (last) player of each category auto-goes to the last remaining team that still needs that category, at 2x base
- Multipliers (editable): wallet reserve 2x, owner-player 3x, last captain 3x, last player in category 2x

10. Bidding conduct
- Only 2 teams bid against each other at a time, a 3rd enters only after one withdraws
- The auctioneer enforces this in the room. The app does not track who is bidding. It only shows this rule on a Rules page.

11. Disputes and audit
- The auctioneer's decision is final on bids, the Auction Committee's on rules
- The admin needs a full audit trail of every action to settle disputes

12. Impact Players (reference only)
- Each team has Impact Players A, B and C. This is a match rule only, no app logic needed.

# Project: EPL Auction Management System

Act as a senior full-stack engineer and AWS solutions architect. Build a complete, production-quality cricket player auction website for a gully cricket tournament.

The application should be simple to operate, visually polished, responsive, real-time and extremely cost-efficient.

**Primary deployment constraint: Use AWS Free Tier eligible resources wherever possible. The expected tournament duration is one month, with approximately 300 simultaneous public viewers and multiple administrators.**

Do not provision AWS resources or incur costs without explicit approval.

---

# 1. TECHNOLOGY STACK

Use the following technologies:

### Frontend
- React
- TypeScript
- Vite
- CSS3
- Responsive design using CSS media queries
- WebSocket client for real-time updates

### Backend
- Node.js
- TypeScript
- AWS Lambda
- Amazon API Gateway (HTTP API + WebSocket API)
- Amazon DynamoDB
- Amazon Cognito for administrator authentication

### Hosting
- Amazon S3 for frontend hosting
- Amazon CloudFront for frontend delivery
- CloudFront-generated URL; no custom domain required.

### Development
- Git and GitHub
- VS Code
- npm

Keep the application modular and maintainable. Avoid unnecessary dependencies and infrastructure.

# 2. USER ROLES

There are two categories of users.

## A. Public viewers

- No registration or login.
- Anyone with the website link can access the auction.
- Public viewers have read-only access.
- They should receive real-time auction updates.
- They cannot modify any information.

## B. Administrators

- Multiple administrators must be supported.
- Each administrator has individual login credentials.
- Use Amazon Cognito for authentication.
- All authenticated administrators share the same auction state.
- Any administrator can manage players, teams and bids.
- Every admin action must be recorded with the administrator's identity and timestamp.

There must be no restriction on multiple administrators accessing the dashboard simultaneously.

# 3. DESKTOP AND MOBILE INTERFACES

Build two distinct viewing experiences within the same React application. 

## Desktop interface

The desktop interface should contain the complete auction dashboard.

Include:

- Admin dashboard.
- Player management.
- Team management.
- Current player auction panel.
- Current bid and base price.
- Team-wise budget information.
- Sold and unsold player lists.
- Auction statistics.
- Bid management controls.
- Auction history.

Administrators should be able to operate the complete auction from a desktop.

## Mobile interface

Mobile devices should display only the public viewer interface.

Display:
- Player photograph.
- Player name.
- Playing role.
- Base price.
- Current bid.
- Current highest-bidding team.
- Auction status: Upcoming, Live, Sold or Unsold.
- Purchasing team, if sold.

Mobile viewers must not see administrative controls or the admin dashboard.

Use responsive CSS and media queries.

IMPORTANT:
Hiding admin controls using CSS is not a security mechanism. All admin operations must be protected by backend authentication and authorization.

The public mobile interface must remain read-only regardless of the device or browser used.

# 4. PLAYER MANAGEMENT

Administrators should be able to:

- Add new players.
- Edit player information.
- Delete players.
- Upload player photographs.
- Set player base prices.
- Assign player roles.
- View all registered players.
- Mark players as eligible or unavailable for auction.

Player information should include:

- Player ID.
- Name.
- Photograph.
- Age (optional).
- Playing role.
- Batting style (optional).
- Bowling style (optional).
- Base price.
- Auction status.
- Final purchase price, if sold.
- Purchasing team, if sold.

Use unique player IDs.

# 5. TEAM MANAGEMENT

Administrators should be able to:

- Create teams.
- Edit team names.
- Delete teams before the auction begins.
- Set initial team budgets.
- View remaining budgets.
- View the list of purchased players.
- View total expenditure.

Each team should maintain:

- Team ID.
- Team name.
- Initial budget.
- Remaining budget.
- Number of players purchased.
- Purchased player list.

Budget calculations must be handled by the backend.

Never allow a team to exceed its available budget.

# 6. LIVE AUCTION FUNCTIONALITY

This is the most important part of the application.

Implement the following workflow:

### Step 1: Select a player

An administrator selects a player and marks them as the current player being auctioned.

The player's information must immediately appear on every connected viewer's screen.

### Step 2: Start bidding

Display:

- Player photograph.
- Player name.
- Playing role.
- Base price.
- Current bid.
- Current highest-bidding team.

### Step 3: Update bids

Administrators can:

- Enter a new bid amount.
- Select the team making the bid.
- Submit the bid.

After successful validation and database persistence, the new bid must immediately appear on every connected viewer's screen.

All administrators should also see the updated state immediately.

### Step 4: Complete the auction

Administrators can mark the player as:

- SOLD
- UNSOLD

If SOLD:
- Record the final purchase price.
- Record the purchasing team.
- Deduct the final price from the team's remaining budget.
- Add the player to the team's roster.
- Update the player's status.

If UNSOLD:
- Mark the player as unsold.
- Do not deduct any team budget.

### Step 5: Next player

Administrators can select the next player and repeat the auction process.

Maintain a complete history of completed auctions.

# 7. BID VALIDATION AND CONCURRENCY

Multiple administrators may update bids simultaneously.

Implement robust server-side validation.

Requirements:

- Prevent simultaneous updates from silently overwriting each other.
- Use DynamoDB conditional writes or transactions.
- Implement auction version numbers or optimistic concurrency control.
- Reject stale bid updates.
- Prevent bids below the base price.
- Prevent a team from exceeding its remaining budget.
- Prevent a player from being sold more than once.
- Prevent invalid auction state transitions.
- Record every successful bid update.
- Include administrator identity and timestamp in the bid history.

The backend must be the single source of truth.

Do not rely on frontend calculations for financial or auction-related validation.

# 8. REAL-TIME COMMUNICATION

Use Amazon API Gateway WebSocket API.

Requirements:

1. Public viewers establish WebSocket connections.
2. Authenticated administrators establish WebSocket connections.
3. Admins submit bid updates through authenticated HTTP endpoints.
4. Lambda validates each bid.
5. Lambda persists the updated auction state in DynamoDB.
6. Only after successful persistence, broadcast the new state to all connected clients.
7. All viewers and admins receive the updated information.
8. Newly connected viewers receive the latest auction state immediately.
9. Handle disconnected clients.
10. Remove stale WebSocket connection IDs.
11. Implement automatic reconnection.
12. Prevent duplicate bid submissions through idempotency mechanisms.

Do not implement continuous polling every second.

Optimize broadcasts to reduce API Gateway message consumption.

# 9. DATABASE DESIGN

Use DynamoDB.

Design suitable tables and access patterns for:

- Players.
- Teams.
- Auction state.
- Bid history.
- Admin-related information, where necessary.
- WebSocket connection IDs.

Use appropriate partition keys, sort keys, indexes and conditional writes.

Ensure the data model supports:

- Retrieving all players.
- Retrieving all teams.
- Retrieving the current auction state.
- Retrieving a team's purchased players.
- Retrieving bid history for a player.
- Retrieving completed auction results.

Avoid unnecessary database scans.

Prefer efficient Query operations and appropriate indexes.

Use transactions when multiple records must be updated atomically, especially when marking a player SOLD and updating the team's budget.

# 10. UI/UX DESIGN

Build a professional sports-auction interface.

Visual direction:

- Dark theme.
- Modern sports tournament aesthetic.
- Clean typography.
- High-contrast bid amounts.
- Large player photographs.
- Green for SOLD and successful operations.
- Red for UNSOLD.

Administrators should be able to update bids quickly without navigating through unnecessary screens.

### Mobile

Prioritize simplicity.

The current player's photograph, name, role, current bid and auction status should be immediately visible.

The interface should work on Android and iOS browsers.
